# Entry-exclusion gold standard — data layout

```
data/elements/<ID>.yaml   SOURCE OF TRUTH. Hand-curated. Edit these.
data/exports/*.tsv|json   GENERATED by 61_build_exports.py. Never edit.
data/seed/genbank/        Frozen GenBank records (in-repo, not scratch).
data/seed/manifest.tsv    accession.version + md5 + fetch date per record.
```

## Why YAML source with TSV/JSON exports

JSON has no comments, and in a curated database **the reason a field is null
carries as much weight as the value** — `partner.status: predicted` needs the
note explaining that adjacency is confirmed but the interaction is untested.

§7 also requires dual independent extraction with reconciliation, which is a
diffing problem. One file per element means two curators never touch the same
file and reconciliation is a per-file diff. Ordered operon gene lists stay
readable. §7's mandated "TSV + JSON" then become build artefacts rather than
things maintained by hand and drifting.

## The adjacency block, and why it has two separate verdicts

`context.adjacency` scores the Garcillán-Barcia & de la Cruz observation, split
into the two claims that are usually conflated:

| field | claim |
|---|---|
| `proximity.within_discovery_window` | within §4 step 2's ±6 kb / ±5 genes window, **both strands** — the rule the pipeline actually implements |
| `synteny.same_strand` + `same_operon` | the stronger structural claim |

SXT is why they must be separate: its `eex` is **32 bp** from `traG` and so is
trivially recovered by the discovery window, but it is transcribed
**convergently** from the P_L regulatory transcript and is not in the *tra*
operon at all. A single boolean either wrongly fails the discovery heuristic or
wrongly asserts operon membership.

`within_discovery_window` is **tri-state**. `null` means unmeasured, which is
distinct from a measured failure — otherwise a gap in the annotation
masquerades as evidence against the heuristic. IncC is `null` (eexC unannotated
in both representatives); R27 is the one genuine `false`.
